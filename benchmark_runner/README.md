# Qwen3-4B runner — unified judge protocol

Default models:

```text
solver:
  /vepfs-mlp2/c20250203/250602012/models/Qwen/Qwen3-4B/

judge:
  /vepfs-mlp2/c20250203/250602012/models/Qwen/Qwen3-14B/
```

## Evaluation policy

The runner now uses only two evaluation classes:

```text
                         ┌─ answer / open-ended ─→ Qwen3-14B unified judge
benchmark result ────────┤
                         └─ executable/verifiable ─→ official verifier
```

Current routing:

```text
ArXivMath                 -> Qwen3-14B judge
OlymMATH                  -> Qwen3-14B judge
PHYSICS (text-only)       -> Qwen3-14B judge
FrontierScience-Olympiad  -> Qwen3-14B judge

LiveCodeBench             -> official executable tests
SciCode                   -> official Inspect + code/HDF5 tests
SWE-bench Pro             -> official repo tests (agent runner still required)
```

MathArena, Math-Verify, SymPy-only scoring, and GPT-4o fallback are no longer
part of the default pipeline.

This protocol is intentionally a **Memory-system comparison protocol**. Scores
from the four answer benchmarks must be reported as `Qwen3-14B judge` scores,
not as their original official-evaluator scores.

## One 14B load for all answer benchmarks

The four answer benchmarks are normalized and concatenated into:

```text
<run_dir>/_unified_answer_judge/judge_input.jsonl
```

Qwen3-14B is loaded once to judge the combined file. Results are then split back
into benchmark directories.

This avoids loading Qwen3-14B four separate times.

## Install

Copy this overlay into the existing repository root. It assumes the previously
tested module still exists:

```text
benchmark_runner/llm_judge/
```

Example:

```bash
cd /vepfs-mlp2/c20250203/public/wc/Memory_encyclopedia
unzip -o memory_encyclopedia_qwen_runner_judge_v2.zip -d .
```

## Doctor

```bash
python -m benchmark_runner.doctor
```

You no longer need `matharena`, Math-Verify, or PHYSICS-specific Python
environments for the default answer benchmark pipeline.

The executable evaluators still keep their isolated environments:

```text
LiveCodeBench -> lcb
SciCode       -> scicode
```

## Recommended first end-to-end smoke

This generates and judges two examples from every answer benchmark:

```bash
export CUDA_VISIBLE_DEVICES=0

python -m benchmark_runner.router \
  --benchmarks arxivmath,olymmath,physics,frontierscience_olympiad \
  --stage all \
  --limit 2 \
  --run-dir runs/qwen3_4b_judge_smoke \
  --resume
```

Expected structure:

```text
runs/qwen3_4b_judge_smoke/
├── _unified_answer_judge/
│   ├── judge_input.jsonl
│   ├── judged.jsonl
│   ├── judged.jsonl.summary.json
│   └── evaluation.*.txt
├── arxivmath/
│   ├── predictions.jsonl
│   ├── judge_input.jsonl
│   ├── judged.jsonl
│   ├── metrics.json
│   └── status.json
├── olymmath/
├── physics/
└── frontierscience_olympiad/
```

Partial answer runs are valid for smoke testing because judge inputs are joined
by task ID rather than by row count.

## Full answer suite

```bash
python -m benchmark_runner.router \
  --benchmarks arxivmath,olymmath,physics,frontierscience_olympiad \
  --stage all \
  --run-dir runs/qwen3_4b_answer_suite \
  --resume
```

All four are generated by Qwen3-4B. After the 4B process exits and releases GPU
memory, all answers are judged in one Qwen3-14B process.

## Add LiveCodeBench

```bash
python -m benchmark_runner.router \
  --benchmarks arxivmath,olymmath,physics,frontierscience_olympiad,livecodebench \
  --stage all \
  --run-dir runs/qwen3_4b_baseline \
  --lcb-env lcb \
  --resume
```

LiveCodeBench still uses its official executable evaluator.

A `--limit` run does not invoke the LiveCodeBench official scorer, because a
partial file is not the canonical release evaluation.

## SciCode

SciCode remains separate because its solver interaction is sequential:

```bash
python -m benchmark_runner.router \
  --benchmarks scicode \
  --stage evaluate \
  --scicode-env scicode \
  --scicode-split test
```

The router starts a local Qwen3-4B OpenAI-compatible vLLM server and lets the
official SciCode Inspect task drive the model.

## SWE-bench Pro

The router deliberately writes:

```text
status = agent_required
```

until a repository-level Qwen3-4B/Memory agent loop is implemented. It will not
report a prompt-only approximation as a SWE-bench Pro score.

## Unified judge input

Every answer benchmark is converted to:

```json
{
  "item_id": "olymmath::<original-id>",
  "original_id": "<original-id>",
  "benchmark": "olymmath",
  "problem": "...",
  "candidate": "...",
  "reference": "...",
  "rubric": "benchmark-specific equivalence rubric"
}
```

Benchmark-specific rubrics cover:

- mathematical equivalence for ArXivMath/OlymMATH;
- all-subpart correctness, units and rounding for PHYSICS;
- science-answer equivalence for FrontierScience-Olympiad.

Candidate text remains untrusted input under the existing judge prompt.

## Metrics

Each answer benchmark gets:

```json
{
  "n_total": 100,
  "n_correct": 60,
  "n_incorrect": 39,
  "n_invalid": 1,
  "accuracy_all": 0.60,
  "accuracy_valid_only": 0.6061,
  "mean_confidence": 0.0,
  "evaluator": "Qwen3-14B unified local judge"
}
```

Use `accuracy_all` as the headline metric. `invalid` is conservatively counted
as not correct.

## Reproducibility

Solver defaults:

```text
Qwen3-4B
thinking       = on
temperature    = 0.6
top_p          = 0.95
top_k          = 20
seed           = 0
max_new_tokens = 8192
```

Judge defaults remain:

```text
Qwen3-14B
thinking       = off
temperature    = 0
```

For a deterministic solver baseline:

```bash
python -m benchmark_runner.router \
  --solver-temperature 0 \
  --solver-top-p 1 \
  ...
```

When comparing:

```text
Qwen3-4B
vs
Qwen3-4B + Memory
```

keep the same tasks, solver sampling configuration, judge model, judge prompt,
and executable evaluators.
